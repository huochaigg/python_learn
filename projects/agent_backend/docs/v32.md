# V32 Structured Output + Pydantic + FastAPI 业务响应

长期项目 `projects/agent_backend/` 的第一版。V1～V31 仍在 `lessons/`，不再复制整套 app。

## 学习目标

`Agent(output_type=...)`、Pydantic、JSON Schema、`final_output` 对象、FastAPI `response_model`、前端按 `type` 渲染卡片。

## 新增 API

`POST /agent/product/analyze`

保留：`POST /agent/chat`、`POST /agent/chat/stream`、Conversation/Message。

## 核心流程

自然语言 → Agent → Tool（MySQL 库存）→ Structured Output（Pydantic）→ Service 用数据库重算 `can_purchase` → FastAPI Response DTO → 前端组件。

三者对比：

- `Agent.output_type`：约束模型最终生成什么。
- `Pydantic.model_validate()`：把对象/dict 校验成模型。
- FastAPI `response_model`：约束 HTTP JSON。

Agent Schema 不必等于 HTTP Schema。本版 Service 会覆盖库存数字，模型不能决定真实下单许可。

Streaming：文本 delta 可直接展示；结构化 JSON 的片段不能当完整对象，不要每个 delta 都 `model_validate`。结束后读 `result.final_output`。SDK 可能有更细的 structured stream event，本版不实现。

业务 Message：`message_type` + `content`。普通聊天 `text` + 纯文本；产品分析把 Response DTO `model_dump_json()` 存进去。SDK Session 仍是模型上下文，两套不是同一个对象。已有表用 `ALTER TABLE ... ADD COLUMN message_type`，默认 `text`，不删表。

## 关键坑点

- 普通 Agent 的 `final_output` 常是 `str`；指定 `output_type` 后才是 Pydantic 对象。
- Tool Result ≠ Agent Final Output。
- Structured Output 校验通过 ≠ 库存事实正确。
- 商品不存在用 `type=not_found`，不要 `stock=0`。
- 官方 `SQLAlchemySession(create_tables=True)` 在 MySQL 上仍会因 VARCHAR 无长度失败，沿用 V31 DDL。
- DeepSeek 等兼容网关可能不支持 `response_format.json_schema`。本版在设置了 `OPENAI_BASE_URL` 时用 `json_object` 覆盖，仍通过 `output_type` 做本地 Pydantic 校验。
