# V33 Handoff + Multi-Agent + Agents as Tools

长期项目 `projects/agent_backend/` 增量版本。不新建 `lessons/v33`，不复制整套 `app/`。

## 学习目标

`Agent.handoffs`、`handoff()`、`on_handoff`、`input_type`、`RunContextWrapper`、`RECOMMENDED_PROMPT_PREFIX` / `prompt_with_handoff_instructions`、`Agent.as_tool()`、`result.last_agent`、Handoff StreamEvent。

重点是**控制权**：谁接管当前轮次、谁生成最终回答、下一轮 HTTP 从谁开始。

## 核心调用链

HTTP `POST /agent/multi/chat`
→ `AgentService.multi_chat`
→ 始终 `Runner.run(triage_agent, ..., session=SQLAlchemySession, max_turns=8)`
→ 模型选择 `transfer_to_inventory_agent` 或 `transfer_to_order_agent`
→ `on_handoff` 记录 `HandoffData.reason`
→ 专家 Agent 调既有 Tool（库存 / 订单 Repository）
→ `result.last_agent` + `handoff_output_item` 作为本轮元数据

Agents as Tools 链：

`Manager Agent` → `ask_inventory_expert` / `ask_order_expert`（`Agent.as_tool()`）
→ 专家跑完返回 Tool Result → Manager 继续生成总结。`last_agent` 仍是 Manager。

## 三个 Demo

1. `demos/v33/01_handoff_basic_demo.py`：`Agent(..., handoffs=[inventory_agent, order_agent])`。问 SKU002 / ORD001，打印真实 Agent 名、Handoff、最终答案，并观察 `agent_updated_stream_event`。
2. `demos/v33/02_handoff_context_demo.py`：`handoff(..., on_handoff=..., input_type=HandoffData)`。打印 `handoff_reasons` 与 `context.user_id`。
3. `demos/v33/03_agents_as_tools_demo.py`：Manager 调用两个专家工具后统一总结。

## Handoff / Agents as Tools / 普通 Function Tool

| | Handoff | Agents as Tools | 普通 Function Tool |
|---|---|---|---|
| 控制权 | 交给目标 Agent，本轮不再回到 Triage | Manager 保留控制权 | 当前 Agent 保留控制权 |
| 上下文 | 目标 Agent 看到对话历史（可 filter） | 专家主要拿到模型生成的 `input` | 当前 Agent 调 Tool，参数是模型生成的函数参数 |
| 最终回答 | 目标 Agent 生成 | Manager 生成 | 当前 Agent 生成 |
| 适合场景 | 明确分诊：库存问题交给库存专家一管到底 | 需要汇总多个专家结果 | 查库、只读查询、无独立人设 |
| 调用链 | Triage → transfer_to_* → Inventory/Order | Manager → as_tool → 专家子 Run → 回到 Manager | Agent → get_product_stock / get_order_status |
| 常见坑 | 当成普通 Tool，以为结果还会回到 Triage；或把 `last_agent` 当成下一轮入口 | 和 Handoff 混用导致控制权混乱 | 让模型写任意 SQL；把鉴权放进 prompt |

供应链例子：

- 用户只问「SKU002 还有多少库存？」→ **Handoff** 给 Inventory Agent。
- 用户问「查 SKU002 库存，再看 ORD001，最后总结」→ **as_tool**，Manager 汇总。
- 专家真正读 MySQL → **Function Tool** + Repository。这不是交接。

## Agent Context

继续用 `AgentContext(db, user_id, handoff_reasons)`。Handoff / as_tool 共用本轮同一个 context。

Handoff **不会**自动创建或关闭 `AsyncSession`。Tool 继续走 Service/Repository。禁止模型生成任意 SQL。

`input_type` 与 `RunContextWrapper.context` 不是一回事：

- `input_type`：模型在交接时生成并被 Pydantic 校验的元数据。
- `ctx.context`：应用层注入的可信依赖。用户身份、租户、数据库都放这里。

提供 `input_type` 时必须同时给 `on_handoff`。

## Session

沿用 V31 `SQLAlchemySession`，`session_id = conversation_id`。

Handoff 后历史仍在同一 Session 里，接收方能看到本轮用户输入和此前条目。下一轮 HTTP 继续传同一个 `conversation_id`。

**应用层策略：每一轮 HTTP 都从 Triage Agent 开始。**

原因：SDK Session 只存 messages，不会替应用层选择下一轮入口 Agent。`result.last_agent` 只描述本轮最终回答者。如果按 `last_agent` 恢复，用户下一句换成订单时可能卡在库存专家里。

本轮交接后的 Agent，和下一次请求从哪个 Agent 开始，是两个问题。

## Streaming

不重做 SSE。Demo 01 观察：

- `agent_updated_stream_event`
- `run_item_stream_event` 中的 `handoff_call_item` / `handoff_output_item`

发给前端前必须转成应用事件。不能把 SDK 对象直接 `json.dumps`。本版 Multi-Agent HTTP 是一次性 JSON，不新增流式接口。

## 真实业务意义

最小供应链助手：Triage 分诊，Inventory 复用已有库存，Order 只读查询。写操作一律拒绝。订单模块以后可以接到传统 Python 供应链后台，不必在本版做完整 OMS。
