## Input / Output / Tool Guardrail

| | Input | Output | Tool Input | Tool Output |
|---|---|---|---|---|
| 时机 | 链首 Agent 开始前（本版 `run_in_parallel=False`） | 最终输出已经生成后 | 每次 Tool 执行前 | 每次 Tool 执行后 |
| 对象 | 用户输入 | `final_output` | Tool 参数 | Tool 返回值 |
| 触发 | `InputGuardrailTripwireTriggered` | `OutputGuardrailTripwireTriggered` | `reject_content` 或 `raise_exception` | 同上 |
| 追回 | 阻塞模式下 Tool 还没跑 | 追不回已经 SSE 发出的 delta | 能阻止本次 Tool | **不能撤销已执行的数据库操作** |

`tripwire_triggered=False`：放行。`True`：中断当前 Run。Guardrail 检查结果是 `output_info`，不是 Agent 最终回答。

`run_in_parallel=True`（默认）：Guardrail 和 Agent 并行，Agent/Tool 可能已经开始。敏感操作必须阻塞。

## Guardrail 与业务校验

- **Pydantic `output_type` / `response_model`**：结构对不对。
- **Guardrail**：策略上允不允许继续跑或把结果交给用户。
- **Repository / Tool 内的 `user_id`**：真权限。模型觉得有权、Prompt 禁止越权、Guardrail 觉得正常，都不能代替。

Input Guardrail 只用确定性关键词，不用 LLM 分类器当安全边界。SKU 格式用正则，库存数字用数据库。

## Input Guardrail 与 Handoff

SDK：`Agent.input_guardrails` 只在**链首 Agent** 运行。Triage 拦住数学题；交接后 Inventory 的每次 `get_product_stock` 不会再跑这份 Input Guardrail。每次 Tool 调用必须靠 Tool Guardrail 或 Repository。

Output Guardrail 作用于**产生最终结果**的那次输出。本版通过 `RunConfig.output_guardrails` 检查整次 Run 的最终输出。

## 异常传播

SDK Exception → `map_sdk_exception()` → `AgentRunError` → FastAPI `@app.exception_handler` → `{code, message}`。

不要把 `str(error)` 或堆栈发给前端。

`max_turns` 限制的是 Agent Loop 轮次，不是聊天历史条数，也不是总 Token 或整次 HTTP 耗时。

## SSE 错误处理

HTTP 响应开始前可以返回 400/502。SSE 已经 `200 + event: start` 之后不能改成 HTTP 500。必须：

```
event: error
data: {"code":"...","message":"..."}
```

然后结束流。禁止在失败时发 `event: done`。

**Output Guardrail 追不回已经发送的文本 delta。** `/agent/guarded/stream` 因此先缓冲正文，审核通过后再一次性发给前端。这和低延迟流式是取舍。Tool 事件仍可即时发送。

## Tool Timeout

`function_tool(timeout=..., timeout_behavior=...)`

- `error_as_result`：超时字符串作为 Tool Result，模型继续。
- `raise_exception`：`ToolTimeoutError`，Run 失败。

超时不代表外部副作用被撤销。本版只用 `asyncio.sleep` 的无副作用函数演示。不要 `time.sleep()`。

## SDK Session 与失败状态

业务 Message：

- 成功：`completed`
- Guardrail 拒绝：`rejected`（不是成功回答）
- SDK/超时等：`failed`
- 用户取消：沿用 V30 的 `failed`

阻塞 Input Guardrail 触发时 Agent 往往还没开始，SDK Session 不一定写入助手最终回答。业务表仍会记一条 `rejected`。不要假设 SDK 会回滚历史，也不要假设中间 Tool item 一定落盘。
